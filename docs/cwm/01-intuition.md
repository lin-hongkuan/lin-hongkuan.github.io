# 01｜先用直觉看懂：CWM 到底在做什么？

如果你只记住一句话，请记住：

> **CWM 把“世界如何变化”与“变化后看起来怎样”拆成两件事。**

前者交给编程智能体和程序，后者交给视频生成模型。

## 先想一个普通视频模型的难题

你给视频模型看一段视频，再说“让快递员穿过港口，到仓库门口停下，途中遇到海马哨兵”。模型要同时猜：

- 快递员是谁、长什么样、现在在哪；
- 港口和仓库之间是什么空间关系；
- “遇到哨兵”会触发什么后果；
- 角色走远、离开镜头后，状态是否还存在；
- 下一个镜头里的角色、位置、物件是否还能接上。

视频只直接提供看得见的结果。角色离开画面以后发生了什么、为什么发生、某个规则是否还在，未必能从几帧图像里可靠地恢复。时间越长、事件越多，单靠视觉历史维护因果状态就越困难。

## CWM 的分工像“导演、场记、摄影组”

可以把它想成一部能互动的影视剧：

- **Coding Agent 像导演/编剧**：理解新事件，决定世界下一步应该怎样变化；必要时修改程序规则。
- **代码像场记和可执行规则**：记录人物、物件、位置、关系、事件，并稳定地执行碰撞、移动、数值变化等重复工作。
- **Proxy 像分镜草图/走位图**：告诉生成模型每一帧主要人物在哪里、怎么移动、镜头怎么走；它故意不画皮肤、布料、灯光等细节。
- **视频模型像摄影与美术部门**：把粗略约束变成有质感的画面和细节动作。

类比只能帮助理解：论文中的组件是 Agent、可执行世界状态、proxy 编译器和视频模型，并非真有导演、场记。

## 一个小例子：国王遇刺之后

假设玩家杀死了某座城的国王，然后离开镜头。

**普通“只看上一段视频”的做法**可能只保留一段视觉上下文：下次回来时，模型不一定记得王位空缺，也不一定会让守卫、商队和派系受到持续影响。

**CWM 的目标做法**可以把事件写入世界状态，让程序持续维护：

```text
事件：国王遇刺
持续状态：王位空缺；城市进入紧急状态
规则：守卫加强巡逻；派系争夺继承权；商贸受到影响
实体：王城、守卫、派系、商队……
```

Agent 负责决定该新增或调整哪些规则；程序反复执行这些规则。等玩家重新来到王城，代码提供仍然有效的状态，proxy 再告诉视频模型如何画出当下景象。

这说明 CWM 所说的“持久”，重点是**世界状态/规则在系统内部持续保存**，不是声称视频模型从未遗忘任何视觉细节。

## 两个计算频率：少数复杂决定 vs 大量重复执行

论文的关键工程直觉之一，是把工作拆成不同节奏：

| 工作 | 频率 / 性质 | 例子 | 谁更适合做 |
|---|---|---|---|
| 高层语义决策 | 较少发生，但需要推理 | 新国王去世后，哪些派系和规则受影响？ | Coding Agent |
| 低层世界更新 | 频繁、重复，最好可复现 | 坐标更新、碰撞、冷却、位置和属性 | 普通程序代码 |
| 画面实现 | 按片段生成，计算成本高 | 人物外观、布料、光照、细节动作 | 视频模型 |

如果每个游戏帧都调用大语言模型来算碰撞和移动，延迟、成本和可复现性都很差。CWM 希望 Agent 不用每一帧都当“人肉游戏引擎”。

## 它与普通文生视频、传统游戏引擎的区别

| 路线 | 优点 | 常见不足 |
|---|---|---|
| 纯文字 → 视频 | 提示简单、视觉自由度高 | 难精确控制逐帧位置、镜头、长时状态 |
| 传统游戏引擎 | 状态与物理规则可控、可重复 | 新内容依赖资产、动画和专门模拟，覆盖面有限 |
| CWM 思路 | 代码维护状态，proxy 提供空间控制，视频模型补视觉细节 | 生成成本/延迟高；Agent 造复杂机制仍不可靠；状态和视觉可能不一致 |

CWM 不是把游戏引擎完全删掉。论文原型实际上**依赖已有游戏代码和基础机制**，由 Agent 在其上组合、扩展、改写；它并未证明 Agent 能从空目录造出 AAA 级完整世界。

## 最容易误解的三件事

1. **“有代码”不等于自动懂物理。** 程序只会执行被写进去的状态与规则；规则是否合理、代码是否正确，仍要检验。
2. **“状态持久”不等于画面每个像素严格一致。** Proxy 是粗粒度约束，视频模型仍需生成外观和局部动态，可能出现偏差。
3. **“世界模型”不自动等于可训练机器人仿真器。** 若要训练具身 Agent，还需测状态准确性、动作响应、失败条件、观测分布与真实环境差异等。
