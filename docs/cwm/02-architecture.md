# 02｜系统结构：状态怎样变成一段视频？

先给全局图。论文里 `S` 表示 world state（世界状态），`A` 表示 action（动作/事件），`O` 表示 observation（观测画面）。

```text
用户意图 / 玩家动作 Aₜ
          │
          ▼
┌─────────────────────────────┐
│ Coding Agent                │  低频：理解新目标/事件、规划
│ 读取状态；选择调用或修改机制 │  需要时才写/改可执行代码
└──────────────┬──────────────┘
               │ 写/调用程序
               ▼
┌─────────────────────────────┐
│ Executable State Sᵉₓₑₜ       │  高频：程序执行确定性更新
│ 实体、属性、规则、关系、历史 │  位置/碰撞/冷却/事件触发等
└──────────────┬──────────────┘
               │ 挑出当前画面需要的状态
               ▼
┌─────────────────────────────┐
│ Proxy Builder + Compiler    │  确定性编译
│ 位置/姿态/轨迹/遮挡/镜头     │  简化形状 → proxy video
└──────────────┬──────────────┘
               │ proxy video + 结构化文本 + 外观锚点
               ▼
┌─────────────────────────────┐
│ Video Model Gθ              │  生成视觉状态 Sᵛⁱˢₜ
│ 按约束画外观、动作和细节     │
└──────────────┬──────────────┘
               │
               ▼
        Observation Oₜ（用户/下游 Agent 看到的视频）
               │
      反馈、动作、事件进入下一轮
               └───────────────────────────────↺
```

## 论文里的状态分解

论文把一个完整状态抽象写作：

```text
Sₜ = (Sᵉˣᵉₜₜ, Sᵛⁱˢₜₜ)
```

- **Executable state（可执行状态）**：程序、实体属性、规则、关系、事件历史以及能被程序操作的变量。
- **Visual state（视觉状态）**：外观、运动等由视频生成过程实现、并需与世界保持一致的视觉信息。

它用抽象公式表达分工：

```text
Sᵉˣᵉₜₜ₊₁ = T_AC(Sᵉˣᵉₜₜ, Aₜ)
Sᵛⁱˢₜₜ₊₁ ~ G_θ(Sᵛⁱˢₜₜ, Sᵉˣᵉₜₜ₊₁)
```

第一式是 Agent 与代码共同推动可执行世界演化；第二式是视频模型根据更新后的状态，生成/更新视觉表现。**这是概念层公式**：论文特别提醒，不表示把全部原始代码直接塞进视频网络。中间还要选取状态、变成文本和 proxy 条件。

## 每个模块究竟输入什么、输出什么？

| 模块 | 输入 | 输出 | 容易踩的坑 |
|---|---|---|---|
| Agent | 用户意图、当前状态、程序执行反馈 | 调用已有机制，或编写/修改可执行逻辑 | Agent 调用并不自动保证规则正确；需要测试与反馈 |
| 世界程序 | 当前变量、动作/事件 | 新变量、新关系、事件结果 | 世界程序可能漏规则、状态冲突、产生不可达状态 |
| Proxy builder | 被选择的实体/状态、相机信息 | 可寻址的粗形状与逐帧约束 | Proxy 丢弃材质、纹理等信息；表达太少会失控，太多会难维护 |
| Proxy compiler | 简化几何及逐帧参数 | 对齐的 proxy 图像序列 | 必须确定、可复现；坐标系/时间戳错位会污染监督 |
| Video model | Proxy video、文本、外观参考等 | 高保真 RGB 帧/视频 | 生成是随机/近似的，可能偏离条件；不是严格物理引擎 |
| Evaluator | 预期状态与输出视频/预测 | 一致性、画质、动态等指标 | 只看漂亮视频不能证明状态正确、因果正确或可交互 |

## 具体代码的节奏示例

以人物走向门口为例：

1. 用户说“走到门边，推开门”。Agent 解析这是一个较高层动作。
2. Agent 查看当前世界，选择 `move_to(door)`、`interact(door)` 之类已有机制；若门的规则不存在，可能修改规则。
3. 普通代码多次更新人物位置、朝向、碰撞和门状态。
4. 系统在若干时间点读取人物位置/姿态、门的开合状态和摄像机运动，生成简化 proxy。
5. 生成模型依据 proxy、文本描述和外观参考生成 RGB 画面。
6. 如输出显示人物没有接近门、或门没开，系统需把观测反馈到后续判断；闭环如何实现取决于具体系统设计，不能只凭框架名假定已经完美解决。

## 论文的 prototype 与“理想框架”要区分

论文把 CWM 描述成 Agent—代码—状态—proxy—视频模型的通用框架。实验原型则是一个更有限的实例：

- Coding Agent 基于**已有闭源游戏代码基础**进行组合、扩展、改写；
- 在运行时录制 proxy 与目标视频；
- 微调 MiniMax H3 以跟随 proxy；
- 用若干多窗口示例展示条件控制和连续生成。

论文明确承认：当前 coding agent 从零可靠实现复杂碰撞、驾驶和高度复杂机制仍困难。不要把概念图误读为已部署的全自动大型开放世界引擎。

## 两条状态通路

状态不会只通过一条通路传递：

- **语义通路**：结构化文本，讲清人物身份、外观、动作语义、规则等。
- **空间/时间通路**：Proxy video，讲清相机与实体逐帧的位置、轨迹、布局、遮挡等。

例如文字写“红衣快递员从画面左侧跑向桥中央”，而 proxy 在每帧用形状标出人物的具体位置、桥的几何布局与镜头运动。文字提供“是谁、做什么”，proxy 提供“在哪、如何随时间移动”。

## 给做研究的同学：这张图能变成什么实验？

可分别在模块接口上测量，而不是只比较最终视频观感：

- Agent 生成的代码是否通过单元测试？状态转移是否满足规则？
- Proxy 中的实例 ID 能否跨帧保持？遮挡后重现能否正确匹配？
- 给定相同状态/种子，proxy compiler 是否逐像素可复现？
- Video model 的人物中心轨迹、镜头轨迹、实体数量与 proxy 相差多少？
- 当状态、proxy、文本互相矛盾时，输出听谁的？错误是否可定位？
