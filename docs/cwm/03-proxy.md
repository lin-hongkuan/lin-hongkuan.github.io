# 03｜Proxy：不是草率画面，而是控制接口

Proxy 可译成**代理表示 / 代理条件**。在 CWM 里，它把代码管理的空间状态转成一段粗略视频，作为生成模型的时空控制条件。

可以把它想成动画制作时的**火柴人走位图**：它不负责好看，而是准确告诉后面的美术/动画系统“谁在哪、往哪走、镜头怎样移动”。

## 为什么只写文字不够？

文字可以描述角色和动作，但细粒度时空要求很难写得既短又准确：

```text
角色一开始在画面左下，2 秒后到中央偏右，镜头跟随并略微绕到背后，
角色经过柱子时短暂被遮挡，随后从柱子另一边出现……
```

把每一帧的坐标、姿态、相对关系都写入文字会很冗长、很费 token，也不代表当前视频模型就能稳定照做。论文报告其测试中，纯文本（即使有专门镜头条件路径）难以精确控制镜头和实体运动。

## 为什么不直接造一套完整 3D？

完整 3D 场景很可控，但需要资产、骨骼、动画、材质、灯光、物理与渲染器。每种新角色、新物体、新动作都可能需要额外制作，成本高且容易把最终视觉锁定在有限资产上。

Proxy 采取折中：**只把当前画面必须遵守的粗空间状态写清楚，外观和细节交给视频模型补足。**

| 表示方式 | 表达重点 | 好处 | 成本/问题 |
|---|---|---|---|
| 结构化文本 | 身份、语义、外观、动作含义 | 灵活，表达新实体方便 | 不易精确指定逐帧位置/遮挡/镜头 |
| Proxy | 粗位置、布局、轨迹、相机、空间关系 | 视频模型能直接读取逐帧空间提示 | 要维护几何和坐标；表达不够会失控，过细则难构造 |
| 完整高质量 3D | 精确几何、材质、骨骼、物理 | 可控、可编辑、可渲染 | 制作/维护成本高，开放词汇和逼真度受资产系统限制 |

## 论文中的 Proxy 可能包含什么？

取决于场景，可能用简单可编程图元表达：

- **实体**：人、动物、车辆、关键道具；
- **位置与尺度**：画面坐标、近似大小；
- **姿态与轨迹**：粗略姿势、逐帧移动方向；
- **场景布局**：地面、建筑、障碍物的空间位置；
- **相机**：视点、运动轨迹、构图变化；
- **遮挡/关系**：谁在谁前面、谁与谁接触或相邻；
- **实例身份**：同一个实体在不同帧中对应的 ID。

这些信号由简单形状或低分辨率表示编译成 proxy video。形状不必像真实人物；只要能够让模型识别“这是要持续跟踪的那个对象、它在这里”。复杂物体如果难以用低成本图元表达，可退化成包围框，只传位置与大致范围，再用文字补身份、外观和动作。

## 信息带宽：Proxy 不是越细越好

Proxy 设计是一个**表达能力—构造难度**的权衡：

- 太粗：模型知道有人，却不清楚手臂动作或与物体的接触位置，生成可能偏离。
- 太细：Agent 要准确建关节、动作、物理状态；这些代码更难写、更难维护，条件也更复杂。
- 更合理的目标：只编码当前生成任务**必须遵守的最小充分状态**。

这和科研里的表示学习、信息瓶颈、控制带宽都有关：要问的不是“proxy 能不能加更多通道”，而是“哪些最少的信息对目标误差最有帮助”。

## 文本与 Proxy 是互补的

```text
结构化文本：这个人是谁？穿什么？正在做什么？整体是什么风格？
Proxy：这个人每一帧具体在哪？摄像机怎样动？与门/桌子空间上怎样对应？
视频模型：把上述条件实现成有纹理、光照、细节动态的 RGB 视频。
```

论文将文本和 proxy 共同作为条件。不能简单说“Proxy 把文字完全替代了”，也不能说“视频模型直接读取代码”。实际是从同一份世界状态选取不同信息，分别序列化成语义和视觉时空信号。

## Proxy 和目标视频必须对齐

训练时，proxy 第 `t` 帧要对应 RGB 目标视频第 `t` 帧。若时间错开 5 帧，模型可能被教成“proxy 在左边，真实人物却在右边也算正确”，监督信号就坏了。

可以把训练样本想成：

```text
条件：外观参考图 + 文字 + 124 帧 proxy
目标：与这 124 帧逐帧同步的 RGB 视频
```

论文的游戏数据从同一游戏运行时同步记录 RGB 和可用于 proxy 的状态；真实视频的 proof-of-concept 则用 KITTI-360 的标定相机位姿、语义 3D 重建与物体标注离线构建条件。

## 公开推理仓库里的具体格式

仓库当前释出的推理实现把条件文件组织为逐帧的：

```text
000000.depth.f32
000000.semantic_id.png
000001.depth.f32
000001.semantic_id.png
...
```

- depth 是 `192×336` 的 little-endian float32，单位米；无效值使用 0。
- semantic ID 是 `336×192` 的 8-bit 灰度图，类别 ID 0–11（如天空、道路、植被、人、动物、车辆、道具等）。
- 每个推理窗口读取 124 帧条件；文本编码器抽样使用其中 11 个时间点（每 12 帧一个）。
- RGB 锚帧与 proxy 条件一起送入公开的 MiniMax H3 Ref2VA 推理路径。

要注意：这份**公开推理条件**（depth + semantic ID）是论文里 proxy 思想的一种具体实例与接口，不代表未来所有 CWM 系统都必须使用同一 proxy 编码。

## Proxy 的优点与风险

**优点**：来自显式状态，可检查、可寻址、可局部编辑；时空约束能沿着代码追踪到来源；不需完整高保真 3D 资产管线。

**风险**：

- 错误的世界状态会被“忠实”编译成错误 proxy；
- 语义类别过粗会把重要物体合并；
- 深度或实例 ID 的对齐错误会造成遮挡/身份冲突；
- proxy 和文本可能互相矛盾；
- 视频模型可能不遵循条件，或画出合理但不符合状态的细节。

因此研究时要同时评估**条件正确性**和**生成服从度**，不能只看最终画面是否漂亮。
